# Ghost Chains Phase 3 (Value Signal) — Brainstorm

**Status:** ideation only, no implementation. Written in response to "are there any findings that can support Phase 3?" — the goal is to separate genuine reuse from wishful pattern-matching before any code is touched.

**Sources:** `ghost_chains/ghost_chains.py` (current, no `created`/temporal-factor parameters — that machinery only exists in the `ghost_chains_diag.py` scratchpad right now), `ghost_chains/challenge statements/ghost_chains_diagnosis.txt`, `ghost_chains.txt` (Phase 1), `ghost_chains_phase2.txt`, `ghost_chains_phase3.txt`, `docs/superpowers/plans/2026-08-22-ghost-chains-phase2.md`.

## Short answer

Two things carry over cleanly and are grounded in Phase 3's own wording; one hypothesized connection (temporal floor → value speed) has no textual support and I'm not recommending it; and there's a real sequencing risk worth naming before writing any Phase 3 code.

---

## 1. The existing BFS walks give reachability, not segmentation — this part of Phase 3 is genuinely new

`_walk` (used for `upstream`/`downstream`/`src_reaches`/`reaches_dst` in `_score`) returns `{node: shortest_hop_distance}` — a reachability *set*, with no memory of which specific edge sequence reached each node or what flowed along it. That's exactly right for Phase 1's structural mass, because Phase 1's own principle is aggregation: *"the combined effect of new or shortened paths between entities, not any single graph feature."* Multiple paths into a node are meant to blend into one decayed weight.

Phase 3 explicitly forbids that same blending for value: *"Do not blindly aggregate amounts across unrelated branches without structural segmentation."* Example 2 (Competing Flow Hypotheses) is the direct proof: Apex Logistics fans out to Cascade (`9800`) and Sterling (`5000`) — two "internally consistent value progressions" that must stay separate. A reachability set has no way to recover "the amount that arrived via this specific path" — it collapses to one distance per node regardless of how many edges got there.

So: **new state is needed**, but it turns out to be small, not a new subsystem. See §5.

## 2. Identity-evasion-as-observable-state is directly reusable — confirmed by Phase 3's own text — but it does *not* have a value-signal twin

Phase 3 says outright: *"an identity attribute that vanishes mid-flow on a connected path... is a distinct evasion pattern — treat the absence as an observable state, not merely a missing value."* That is a verbatim description of what `_identity_mass` already does today (the `value is None` branch: scans `self._active` for a direct predecessor into `src` that *did* carry the attribute, and fires `W_IDENTITY_EVASION` on the drop). Phase 3 isn't asking for new identity logic — it's confirming the existing Phase 2 mechanism stays load-bearing unmodified. Nothing to design here; this is validation, not a task.

I looked for a value-signal analogue ("a broken amount trail" as an absence) and don't think one exists in the spec: `amount` is a **required** field (unlike `ipAddress`/`deviceId`), so there is no "missing amount" state to observe — every transaction has a number. The Phase 3 equivalent of "something went wrong in the trail" isn't absence, it's the *reversal/inconsistency itself* (Example 3), which is a different kind of signal (a numeric-relationship violation, not a dropped optional field). I'm flagging this so we don't force a parallel that doesn't hold — the two mechanisms rhyme thematically ("the model should react to an anomaly appearing mid-flow") but need different code.

## 3. Temporal floor → "speed of value decay": no textual support, not recommending it

I looked for a reason the just-validated temporal-dampening mechanism (fast structural closure = more suspicious, per the parent session's experiment against `ghost_chains_diag.py`) might generalize to value (e.g., "a fast multi-hop value decay is more suspicious than a slow one"). Phase 3's doc never mentions elapsed time in connection with amounts — the four examples and their interpretations are entirely about the *numeric relationship* between consecutive amounts on a path, with timestamps present only as ordinary sequencing, not as a scored dimension. Manufacturing a time-weighted value term here would be exactly the "tuned to a plausible-sounding pattern with no evidence behind it" failure mode the Structural Consistency dimension penalizes. Leaving this out.

One real (separate) connection worth noting: `docs/superpowers/plans/2026-08-22-ghost-chains-phase2.md`'s own Step 2 snippet shows `_score(self, src, dst, created, ip, device)` with a comment about "the cycle temporal-factor scaling" — meaning temporal weighting was present in `ghost_chains.py` at some earlier point in this project's history and was since removed (the file now takes no `created` parameter at all). That's context for the parent session's temporal-floor work, not for Phase 3 — mentioned here only so it isn't mistaken for a new finding if it resurfaces later.

## 4. Sequencing risk: Phase 3 evaluation re-tests Phase 1, and Phase 1 already has confirmed high-severity gaps

Every phase doc repeats the same clause: *"Each phase's evaluation re-tests the requirements of every earlier phase within the same evaluation run."* The diagnosis doc records a real evaluation result against the current engine: `STRUCTURAL_DEVIATION: High, TEMPORAL_DEVIATION: High` — at Phase 1, before any Phase 3 signal exists. Phase 3 adds `VALUE_FLOW_DEVIATION` and `CROSS_SIGNAL_DEVIATION`, and by definition `CROSS_SIGNAL_DEVIATION` measures whether structural + identity + value cohere *together* on scenarios like the doc's own cross-signal examples.

Since every term (structural, identity, and any new value term) is summed additively into the same `mass` before the single saturating transform (`1 - (1 + mass/SATURATION)^-TAIL`), an unresolved structural/temporal miscalibration doesn't stay isolated — it shifts the baseline that value and cross-signal scores are built on top of. Concretely: if we ship a value term now and then evaluate, a `CROSS_SIGNAL_DEVIATION: High` result would be genuinely ambiguous — we wouldn't know whether it's the new value logic or the already-known structural/temporal gap bleeding through the shared sum. That ambiguity is exactly what the diagnosis doc's own priority order was trying to avoid (close Temporal via experiments A/E, then Structural via B/C, *before* adding new signal surface).

This isn't a reason to stop thinking about Phase 3 — the ideation here is cheap and worth having ready — but actual wiring/evaluation of a value term is better sequenced *after* the Phase 1 structural/temporal experiments the parent session is already running land cleanly, so any `VALUE_FLOW_DEVIATION`/`CROSS_SIGNAL_DEVIATION` feedback can be attributed to the new code rather than inherited noise.

## 5. Design sketch (ideation, not code)

If/when this gets built, the natural shape — matching how Phase 2's identity signal was bolted on as one more additive term, not a parallel scoring system:

- **New state:** extend the existing `self._active[tx_id]` tuple from `(src, dst, ip, device)` to `(src, dst, ip, device, amount)`. `amount` already arrives in `_process_one`'s `raw` dict (currently only read by `_fingerprint` for idempotency) — this is a one-field extension of a structure that already exists and is already 24h-pruned, not a new index to keep in sync. Same pattern Phase 2 used.
- **Scoring principle, mirroring `_identity_mass`'s one-hop predecessor/successor check** (not the full-reachability walks — see §1 on why aggregation is wrong here): for each active edge `p -> src` in `self._active`, compare this transaction's `amount` to `p`'s amount as a retention ratio. A ratio in `(0, 1]` — value held steady or reduced — is the *expected* layering signature and should contribute little-to-nothing (Example 1's last hop: `9732.42 / 9820.81 ≈ 0.991`, consistent with the established ratio, lowest risk of the four). A ratio `> 1` — value increased relative to the immediate predecessor on a structurally continuous path — is the reversal signal and should dominate (Example 3's last hop: `9950 / 9800 ≈ 1.015`, highest risk of the four).
- **Why this needs no cross-branch reconciliation:** in Examples 2 and 4, Apex Logistics has exactly one inbound edge (from Meridian), so both outgoing branches (Cascade, Sterling) independently compare against that *same single* predecessor — there's no ambiguity about "which predecessor" to use, and no need to merge the branches' ratios into one global figure. This matches the spec's "no single global value ratio applies across the full graph" for Example 2 without any extra segmentation logic — the one-hop-predecessor design is naturally branch-local already.
- **A non-obvious consequence worth testing explicitly:** under this design, Examples 2 and 4 would likely score *similarly and unremarkably* on the value term alone (both branches show ordinary retention ratios in both examples) — the doc's declared "not directly comparable" split between them may be almost entirely a **structural** fan-out-vs-convergence distinction (Phase 1's existing `fan`/pair-mass terms), with value contributing confirmation rather than differentiation. If true, that's a good sign: it means Phase 3 doesn't need to invent new logic to explain 2-vs-4, just needs the value term to stay quiet when the pattern is ordinary and loud when it's violated.
- **Cross-signal examples in the doc** (Phase1+2, Phase1+3, Phase2+3) are consistent with this shape — each is described as structural/identity/value being *"simultaneously present,"* i.e., independently computed and summed, which is what the additive-mass architecture already does. No evidence in these examples that the terms need to interact multiplicatively or conditionally on each other, beyond what pure summation already gives.

## Open questions (for whoever picks this up)

- Is a one-hop predecessor check sufficient, or does a longer chain (Example 1's 4 hops) require checking consistency across the *whole* established ratio, not just the last link? The single documented reversal case (Example 3) only requires a 1-hop check to catch, but the spec's "the trail of amounts can confirm or contradict a pattern" phrasing hints the reference model may look further back than one hop.
- What weight/shape converts the retention ratio into a mass term? (`W_VALUE_REVERSAL * f(ratio)` — `f` needs to be ~0 for ratio ≤ 1 and grow for ratio > 1; exact curvature is an open tuning question, same category as the Phase 1 `W_*`/`SATURATION`/`TAIL` knobs already flagged as unresolved in the diagnosis doc.)
- Should convergence (Example 4: two branches arriving at the same node) trigger anything extra when their *retained* amounts land close together at the shared destination, beyond what Phase 1's existing fan-in term already scores structurally? The doc's interpretation text ("value trajectories that arrive at Horizon Capital remain distinct") suggests distinctness itself might matter, not just each branch's internal consistency — that would need genuinely new logic beyond §5's sketch.
